```

│   ├── Enums/                    # MessageTypeEnum, LogSensitivityLevelEnum

```

## Layer Responsibilities

### API Layer (`Avatier.Api`)

- Receives HTTP requests and delegates to the service layer.
- Translates `Response` / `Response<T>` wrappers into appropriate HTTP status codes.
- Hosts the Scalar interactive API reference and OpenAPI document (development only).
- Configures Serilog with a Console sink (all environments) and a Seq sink (development).
- Owns no business logic—its only job is request routing and HTTP semantics.

### Service Layer (`Avatier.Service`)

- Contains all LDAP interaction logic in `LdapService`.
- Uses `System.DirectoryServices.Protocols` (cross-platform, low-level LDAP client) for maximum control over LDAP operations.
- Validates inputs and returns structured `Response` objects for every expected outcome.
- Extends `BaseLayer` for consistent, sensitivity-aware logging.

## Observability & Developer Experience

### Seq – Structured Log Server

[Seq](https://datalust.co/seq) is a centralized structured-log server used as the primary log sink in development. The application writes logs via **Serilog** (`Serilog.Sinks.Seq`), and Seq ingests, indexes, and exposes them through a web UI for real-time searching and filtering.

| Detail | Value |
|--------|-------|
| Docker image | `datalust/seq:2024` |
| Ingestion port | `5341` (HTTP) |
| Web UI | `http://localhost:8100` |
| Default admin | `Admin` / `Admin@123` |

**Configuration path:** The Seq sink is wired in `appsettings.Development.json` under `Serilog.WriteTo`, pointing to `http://localhost:5341`. In production (`appsettings.json`) only the Console sink is enabled, so Seq is strictly a development-time dependency.

The combination of Seq with the sensitivity-aware logging in `BaseLayer` means developers get full debug-level structured logs in Seq during development, while production sinks never receive sensitive data above the configured threshold.

### Scalar – Interactive API Documentation

[Scalar](https://scalar.com) replaces the traditional Swagger UI with a modern, interactive API reference. The `Scalar.AspNetCore` package reads the OpenAPI document generated by **NSwag** and renders it as a polished, developer-friendly page.

| Detail | Value |
|--------|-------|
| Package | `Scalar.AspNetCore` |
| Route | `/scalar/v1` (default) |
| Enabled in | Development only |

**Registration in `Program.cs`:**

1. `AddOpenApiDocument()` (NSwag) generates the OpenAPI spec with title, version, and description.
2. `MapScalarApiReference()` maps the Scalar UI, configured with a custom title and a default HTTP client preset (`CSharp` / `HttpClient`) so generated code snippets match the project's language.

Both `UseOpenApi()` and `MapScalarApiReference()` are gated behind `app.Environment.IsDevelopment()`, ensuring the documentation endpoint is never exposed in production.

## Key Design Decisions

### 1. Response Wrapper Pattern

Every service method returns `Response` or `Response<T>`. Messages carry a `MessageTypeEnum` that distinguishes `Success`, `Information`, `Warning`, `Validation`, and `Error`. The `IsInFailure` property (`true` when any message type > `Success`) lets controllers decide the HTTP status without inspecting message text.

**Expected errors** (user not found, invalid password, duplicate group member) are communicated via messages inside the wrapper—never thrown as exceptions.

**Unexpected errors** (LDAP server unreachable during a non-connectivity-test operation, network timeout) are allowed to propagate as exceptions, which correctly surface as 500 responses.

The one exception to this rule is `TestConnection`, whose entire purpose is to probe connectivity; there, `LdapException` is caught and wrapped since a connection failure is the expected negative outcome.

### 2. Sensitivity-Aware Logging (`BaseLayer`)

All logging passes through `BaseLayer.Log()`, which checks the message's `LogSensitivityLevelEnum` against the configured threshold before forwarding to `ILogger`. This prevents accidental leakage of sensitive data (user DNs, passwords) into log sinks in production while still allowing full debug output in development.

### 3. LDAP Filter Escaping

All user-supplied values interpolated into LDAP filters go through `EscapeLdapFilter()` (RFC 4515) to prevent LDAP injection.

### 4. Separation of Admin vs User Connections

- **Admin connection** (`CreateAdminConnection`): used for searches, attribute modifications, and password resets.
- **User connection** (`CreateUserConnection`): used to verify a user's current password (bind-as-user) before allowing password changes, and for the authentication endpoint.

This means the admin password is never exposed to the user, and user passwords are verified by the LDAP server itself—not compared in application memory.

## Error Handling Strategy

| Scenario | Mechanism | HTTP Result |
|----------|-----------|-------------|
| Missing/invalid input | `Validation` message in `Response` | 400 |
| User/group not found | `Validation` message in `Response` | 400 / 404 |
| Duplicate group member | `Warning` message in `Response` | 400 |
| Wrong password on auth/change | `Validation` message in `Response` | 400 / 401 |
| LDAP server unreachable | `LdapException` propagates | 500 |
| Connection test failure | `Error` message in `Response` | 503 |

## How This Solution Could Evolve

### Short Term
- **Unit tests**: mock `LdapConnection` behind an abstraction to test `LdapService` logic without a running directory.
- **Pagination**: LDAP paged results control for directories with thousands of entries.
- **Create / delete users**: extend the service with `AddRequest` / `DeleteRequest` operations.

### Medium Term
- **Caching**: cache frequently-read user/group data with short TTLs to reduce LDAP round-trips.
- **Connection pooling**: reuse `LdapConnection` instances via a pool instead of creating one per request.
- **LDAPS / StartTLS**: enforce encrypted connections in production.

### Long Term
- **Multi-directory support**: abstract `ILdapService` behind a provider pattern to support Active Directory alongside OpenLDAP.
- **Event sourcing / audit log**: record every identity change for compliance.
- **RBAC on the API**: protect admin-level endpoints (attribute editing, group management) behind role-based authorization using the LDAP groups themselves.
